---
title: D1
description: Declare one database and query it safely through request-scoped sessions.
---

Declare one Cloudflare D1 database in `goribu.config.js`:

```js
import { defineConfig } from "goribu/server";

export default defineConfig({
  name: "my-app",
  compatibilityDate: "2026-09-03",
  database: { type: "d1", name: "my-app-db" },
});
```

Goribu owns the generated `DB` binding in development and production. Do not add
a second `d1_databases` declaration; the build refuses competing owners.

## Query from a handler

Use the request-scoped `req.d1` tagged template. Interpolated values become D1
bindings rather than SQL text:

```js
export async function GET(req, res) {
  const posts = await req.d1`
    SELECT id, title
    FROM posts
    ORDER BY created_at DESC
    LIMIT ${20}
  `.all();

  return res.render({ posts });
}
```

A statement is lazy until one terminal method runs:

| Terminal | Result |
|---|---|
| `.get()` | First row, or `null`. |
| `.all()` | All rows, or `[]`. |
| `.value()` | First column of the first row, or `null`. |
| `.run()` | `{ changes, lastRowId }` for writes and DDL. |

Awaiting the statement itself rejects and teaches you to add a terminal method.
Strings, numbers, booleans, `null`, binary values, and non-empty arrays can be
bound. Convert dates and structured data explicitly.

## Atomic application writes

Pass unexecuted statements to `atomic()` when all must apply or none may apply:

```js
await req.d1.atomic([
  req.d1`INSERT INTO posts (id, title) VALUES (${id}, ${title})`,
  req.d1`INSERT INTO tags (post_id, name) VALUES (${id}, ${tag})`,
]);
```

D1 has no interactive transaction that can pause for application code between
statements.

## Read-your-writes

The default facade opens one lazy D1 session per request. With replication
enabled, Goribu advances a short-lived `goribu_d1_bookmark` cookie before the
response, so a redirect following a write sees that write:

```text
POST /feedback → INSERT → 303 + bookmark
GET  /feedback → bookmarked session → new row is visible
```

Use `req.d1.fresh` for a primary-first authorization, balance, or quota read. Use
`req.d1.public` for shared data that may tolerate replica lag. Neither mode
changes HTTP caching.

```js
const account = await req.d1.fresh`SELECT * FROM accounts WHERE id = ${id}`.get();
const posts = await req.d1.public`SELECT * FROM posts ORDER BY created_at DESC`.all();
```

## Schema belongs in migrations

Do not run `CREATE TABLE IF NOT EXISTS` on every request. Put schema history in
numbered files, apply it locally before using the route, and inspect production
before deployment:

```sh
goribu migrate:new create posts
goribu migrate
goribu check
```

`goribu deploy` provisions the database and applies pending production migrations
before uploading the Worker. Migration failure blocks the upload.

To look at the data, run SQL from the terminal with `goribu d1`, local by
default:

```sh
goribu d1 "SELECT id, title FROM posts ORDER BY id DESC LIMIT 5"
```

With `--remote`, any SQL other than a single `SELECT` needs the database name
typed at a terminal. See [the CLI](/docs/cli).
