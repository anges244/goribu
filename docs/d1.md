# D1

D1 is Cloudflare's managed SQLite database and Goribu's built-in SQL store. An
application declares one database in `goribu.config.js`:

```js
import { defineConfig } from "goribu/server";

export default defineConfig({
  name: "my-app",
  compatibilityDate: "2026-09-03",
  database: { type: "d1", name: "my-app-db" },
});
```

For your own Postgres database instead, see [Postgres](./postgres.md); an app
declares one `database`.

Goribu gives the Worker a `DB` binding in development and production. Do not add
your own `d1_databases` declaration: Goribu owns that binding and fails the build
when both configuration paths try to define it.

Run `goribu check` to inspect the production plan without changing anything.
The first `goribu deploy` creates a missing database, attaches its UUID to the
generated binding, and deploys the Worker. Later deploys reuse the same database.

## Safe queries

Handlers query the database through the `req.d1` tagged template. Interpolated
values become bound parameters; they never become part of the SQL text:

```js
export async function GET(req, res) {
  const post = await req.d1`
    SELECT id, title
    FROM posts
    WHERE id = ${req.params.id}
  `.get();

  if (post === null) return res.notFound();
  return res.render({ post });
}
```

Strings, numbers, booleans, `null`, and binary values are accepted. Booleans are
bound as `1` or `0`. A non-empty array expands into multiple placeholders:

```js
const posts = await req.d1`
  SELECT id, title FROM posts WHERE id IN (${ids})
`.all();
```

Empty arrays, `undefined`, dates, objects, nested arrays, functions, symbols, and
bigints are rejected with an error that explains the required conversion. Use
`date.toISOString()` for dates and `JSON.stringify(value)` for JSON data.

A query remains lazy until a terminal method runs:

| Terminal | Result |
| --- | --- |
| `.get()` | First row as an object, or `null`. |
| `.all()` | All rows, or `[]`. |
| `.value()` | First column of the first row, or `null`. |
| `.run()` | `{ changes, lastRowId }` for writes and DDL. |

Always choose a terminal method. Awaiting the statement itself rejects instead
of silently doing nothing:

```js
await req.d1`DELETE FROM posts WHERE id = ${id}`; // Error: add .run()
```

## Writes and atomic batches

Use `.run()` for an insert, update, delete, or schema statement:

```js
await req.d1`
  INSERT INTO posts (title, created_at)
  VALUES (${title}, ${new Date().toISOString()})
`.run();
```

Use `req.d1.atomic()` when several statements must all apply or none may apply.
Pass unexecuted statements, without terminal methods:

```js
await req.d1.atomic([
  req.d1`INSERT INTO posts (id, title) VALUES (${id}, ${title})`,
  req.d1`INSERT INTO tags (post_id, name) VALUES (${id}, ${tag})`,
]);
```

The result is an array in statement order; each entry contains `rows`, `changes`,
and `lastRowId`. D1 does not provide interactive transactions, so application
code cannot read, branch in JavaScript, and then continue the same atomic unit.

Database failures are wrapped without hiding the original cause. Recognized
SQLite constraint failures add `constraint`, `table`, `columns`, or
`constraintName` fields so handlers can turn them into application responses.

## Sessions and read-your-writes

With replication enabled, reads may run on a nearby replica while writes run on
the primary. A replica can briefly lag behind a write. Goribu prevents a visitor
from losing sight of their own changes by opening one lazy default D1 session per
request and carrying its position in the `goribu_d1_bookmark` cookie.

The bookmark is committed to the response before Goribu flushes cookies. A
browser therefore sends the advanced bookmark on a redirect's follow-up request:

```text
POST /feedback  → INSERT → 303 + goribu_d1_bookmark
GET  /feedback  → bookmarked session → the inserted row is visible
```

The cookie is `HttpOnly`, `Secure`, `SameSite=Lax`, has `Path=/`, and expires
after one hour. Requests that never use `req.d1` do not read `env.DB`, open a D1
session, or emit a database bookmark.

If D1 rejects an incoming bookmark as invalid before executing the first
operation, Goribu discards it and retries that operation once in an
unconstrained session. Other database failures are never replayed: retrying a
write after an ambiguous failure could apply it twice.

The default mode is the right choice for application data tied to the visitor:

```js
const posts = await req.d1`SELECT id, title FROM posts`.all();
```

Two explicit alternatives cover different freshness needs:

```js
// Run this statement against the primary.
const account = await req.d1.fresh`
  SELECT * FROM accounts WHERE id = ${id}
`.get();

// Use an unconstrained nearby copy without the visitor bookmark.
const posts = await req.d1.public`
  SELECT id, title FROM posts ORDER BY created_at DESC
`.all();
```

Use `fresh` for authorization, balances, quotas, or another read that must include
every committed write. It does not change the visitor's default bookmark. Use
`public` for shared data that does not depend on who is reading; it may be briefly
behind. `public` alone does not make the HTTP response cacheable.

Freshness modes cannot be chained. `atomic` belongs to the default facade; a
fresh or public statement passed to it is rebound to the batch's owning session.

### Replication configuration

The `replication` field has three states:

```js
// Enable replication when Goribu creates the database; do not change an existing one.
database: { type: "d1", name: "my-app-db" }

// Reconcile the database so replication is enabled.
database: { type: "d1", name: "my-app-db", replication: true }

// Reconcile the database so replication is disabled.
database: { type: "d1", name: "my-app-db", replication: false }
```

With replication disabled, every mode uses the raw binding, no session is opened,
and no bookmark cookie is set.

## Dynamic SQL

Use `req.d1.unsafe(text, params)` only when SQL structure must be selected at
runtime. Values still belong in the parameter array:

```js
const columns = { newest: "created_at", title: "title" };
const column = columns[req.query.get("sort")] ?? "created_at";

const posts = await req.d1
  .unsafe(`SELECT id, title FROM posts ORDER BY ${column} LIMIT ?`, [20])
  .all();
```

The lookup makes `column` one of the SQL fragments written by the application.
Never insert request, parameter, or form values into `text`. Unlike the tagged
template, `unsafe()` can create a SQL-injection vulnerability.

Tagged templates cannot be nested or joined, so most variation is better
expressed in SQL itself, with every value still a parameter.

**Optional filters.** Bind `null` for "no filter" and let SQL skip the condition.
`undefined` is rejected, so convert a missing value with `?? null`:

```js
const status = req.query.get("status") ?? null;

const posts = await req.d1`
  SELECT id, title FROM posts
  WHERE (${status} IS NULL OR status = ${status})
  ORDER BY created_at DESC
`.all();
```

**Lists.** An empty array is rejected, because `IN ()` is not valid SQL and
Goribu will not guess whether it means "nothing" or "everything". Decide before
querying:

```js
if (ids.length === 0) return res.json([]);
const posts = await req.d1`SELECT id, title FROM posts WHERE id IN (${ids})`.all();
```

**Ordering.** Choose between fixed orders with `CASE`, or select a column from an
allowlist with `unsafe()` as above:

```js
const sort = req.query.get("sort") === "title" ? "title" : "newest";

const posts = await req.d1`
  SELECT id, title FROM posts
  ORDER BY CASE WHEN ${sort} = 'title' THEN title END,
           created_at DESC
`.all();
```

**Many optional conditions.** When the conditions themselves vary, build the
text from fragments your code wrote and keep values in the parameter array:

```js
const where = [];
const params = [];
if (status) { where.push("status = ?"); params.push(status); }
if (authorId) { where.push("author_id = ?"); params.push(authorId); }

const posts = await req.d1
  .unsafe(
    `SELECT id, title FROM posts${where.length ? ` WHERE ${where.join(" AND ")}` : ""} LIMIT ?`,
    [...params, 20],
  )
  .all();
```

`unsafe()` parameters are a flat list of scalars: arrays do not expand, so
write one `?` per list element yourself.

## Text search and case

SQLite's `LIKE` ignores case only for ASCII letters, and `lower()` and `upper()`
change only ASCII letters. `'Ελλάδα' LIKE 'ελλάδα'` is false. For case- or
accent-insensitive search in other languages, store a normalized copy written by
your code and search that column with a value normalized the same way:

```js
// Write: keep search_text next to the original title.
const normalize = (text) =>
  text.normalize("NFD").replace(/\p{M}/gu, "").toLocaleLowerCase();

await req.d1`
  INSERT INTO posts (title, search_text) VALUES (${title}, ${normalize(title)})
`.run();

// Read: escape LIKE wildcards in the user's input with "!".
const term = normalize(query).replace(/[!%_]/g, "!$&");
const posts = await req.d1`
  SELECT id, title FROM posts WHERE search_text LIKE ${`%${term}%`} ESCAPE '!'
`.all();
```

## Raw access

Query builders can use the session objects while retaining their consistency
semantics:

```js
import { drizzle } from "drizzle-orm/d1";

const db = drizzle(req.d1.session);
const freshDb = drizzle(req.d1.fresh.session);
const publicDb = drizzle(req.d1.public.session);
```

`req.d1.fresh.session` starts at the primary, but later operations may use a
replica while remaining sequentially consistent. The tagged
``req.d1.fresh`...` `` form starts a new primary session for each terminal
operation. Use `req.d1.binding` only when an integration specifically requires
the plain Cloudflare `D1Database` binding.

## Schema migrations

Schema history belongs in numbered SQL files under `migrations/`, not in request
handlers. Create and apply the first local migration before a route queries its
table:

```sh
goribu migrate:new create feedback
# Write the SQL in migrations/0001_create-feedback.sql.
goribu migrate
```

`goribu check` reports the real production applied, pending, and drift state.
`goribu deploy` applies pending production migrations after provisioning D1 and
before uploading the new Worker. See [Migrations](./migrations.md) for the file
contract, manual early migration, undoing changes, seed guard, and safe
expand-and-contract order.

## Inspect data from the terminal

Query local D1, the database `goribu dev` uses, with `goribu d1`:

```sh
goribu d1 "SELECT id, title FROM posts ORDER BY id DESC LIMIT 5"
```

`--remote` queries production. Any SQL other than a single `SELECT` needs the
database name typed at a terminal first. See
[`goribu d1`](./cli.md#goribu-d1).

## Missing bindings

Using `req.d1` without the generated `DB` binding fails closed with a repair
instruction. Declare the database in `goribu.config.js`, restart development or
rebuild, and let Goribu synthesize the binding. It never silently skips a query.
