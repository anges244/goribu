# Goribu decisions

This log records Goribu's settled design forks. A row is added when the decision
is actually embodied in this tree; decisions carried over from the previous
version are ported here as their code lands, not before. Append a row whenever
implementation resolves a new fork.

| Date | Block | Decision | Chosen | Why (1 line) | Alternatives |
|---|---:|---|---|---|---|
| 2026-08-23 | 1 | Node floor | Node `>=22` | Keeps framework tooling on the current modern API baseline. | Node `>=20` |
| 2026-08-23 | 1 | Export map | Four entries: `.`, `./server`, `./client`, `./vite` | Explicit runtime and build boundaries help prevent code leaks. | Fold `./vite` into `./server` |
| 2026-08-31 | 1 | Application config channel | One branded `defineConfig()` from `goribu/server` starting with the deploy fields `name`, `compatibilityDate`, `compatibilityFlags`; runtime fields (`Document`, `responseHeaders`, `database`) are added to this same validator as later blocks land their consumers | The config feeds Wrangler synthesis first; the previous version's config was coupled to parked/absent code (Postgres, response headers, database, Document) so it is grown field-by-field rather than copied wholesale | Copy the previous config wholesale, or split deploy and runtime config into separate files |
| 2026-08-31 | 1 | Production build engine | `goribu build` runs one `vite build` through `@cloudflare/vite-plugin`, which emits the workerd-targeted Worker bundle, the client bundle, and a deploy-ready `wrangler.json` from the app's Wrangler config; `goribu()` composes it and points the client build at `src/client-entry.js` | Uses the platform's own Vite integration so a single pass produces deploy-ready output, rather than maintaining a bespoke bundler | Hand-rolled two-pass Vite build, or Vite for the client and Wrangler for the Worker |
| 2026-08-31 | 1 | Deploy scope | `goribu deploy` deploys to production only, run by hand; preview/versioned deploys and any CI pipeline are deliberately left out for now, and deploying is documented in `docs/deploy.md` | Preview deploys are premature — they surface shared bindings, the versions-vs-deployments distinction, and CI implementation questions that Goribu has not answered yet; production-only keeps the pipeline honest until those are decided | Per-version preview URLs via `wrangler versions upload`, or automated per-commit deploys via CI |
| 2026-08-31 | 1 | Deploy engine | `goribu deploy` runs the production build, then spawns Wrangler's `deploy` (Wrangler is a direct `goribu` dependency); the build's `.wrangler/deploy/config.json` redirect points Wrangler at the generated Worker bundle and `dist/client` static assets, and Wrangler owns Cloudflare authentication | Wrangler is Cloudflare's own deploy tool and the Vite plugin already emits a deploy-ready redirect for it, so uploading through it needs no bespoke uploader or credential handling | Call the Cloudflare API directly, or shell out to a globally installed `wrangler` / `npx wrangler` |
| 2026-08-31 | 1 | Development server engine | `goribu dev` starts Vite's dev server (`createServer`) at `process.cwd()`; the same `goribu()` plugin composition serves the generated `.goribu/worker.js` through workerd (via `@cloudflare/vite-plugin`) with HMR, so dev and production run one pipeline | Reuses the platform's own Vite/workerd dev integration so the local server runs the real Worker, rather than a bespoke dev worker or a hand-driven Miniflare | Hand-rolled dev worker, or drive Miniflare/wrangler directly outside Vite |
| 2026-08-31 | 1 | Wrangler configuration source | Synthesized into `.goribu/wrangler.json` from `goribu.config.js` (`name`, `compatibilityDate`, `compatibilityFlags`) and fed to `@cloudflare/vite-plugin` via `configPath`; the app never hand-writes a Wrangler file | `goribu.config.js` is the one channel that owns deploy identity, so a hand-written Wrangler file would be a second source of truth that could silently drift | Hand-written `wrangler.jsonc`, or a generated Wrangler file at the project root discovered automatically |
| 2026-08-31 | 1 | Generated Worker entry (skeleton) | The Vite plugin generates `<projectRoot>/.goribu/worker.js`, which streams one hardcoded page (`src/page.jsx`) through `renderToReadableStream` for every request; there is no routing yet | A generated entry (not hand-written) proves the render path end to end while staying trivial; Block 2 generalizes the single hardcoded page into a scanned route tree | Hand-write the Worker entry, or hardcode the page inside the framework rather than the app |
| 2026-09-01 | 2 | Where a custom Document lives | An optional top-level `src/routes/_document.jsx`, discovered like `_404` and compiled by Vite into the Worker, with a framework default when absent; `goribu.config.js` stays Node-loadable data and rejects a `Document` field with a teaching error pointing at `_document.jsx`. General rule: **config is data** (no JSX, no React, no application modules); **anything that renders is a file** in the module graph | `goribu.config.js` is read by Node for the CLI, Wrangler synthesis, `check`, and provisioning — none involve React, and Node cannot even import a `.jsx` file; a Document belongs in the render graph, where it also gets HMR, styles, and the client-boundary audit. This supersedes the Block 1 row's anticipation that `Document` would sit on the config | Put `Document` on `goribu.config.js` (breaks Node config loading on JSX); load `goribu.config.js` through Vite so config can carry React modules |
| 2026-09-01 | 2 | Catch-all and optional route segments | Not supported in this version: a `[...param]` or optional segment is rejected at manifest generation with a teaching error. Only static segments and single `[param]` dynamic segments exist | One implementation until there is a second — no route in the fixture or the coming site needs a catch-all yet, and fixing its precedence rules before a real case invites guesses; the absence is written down so "not yet" stays visible | Ship `[...param]` catch-alls and their precedence rules now, ahead of a consumer |
| 2026-09-01 | 2 | Trailing-slash canonicalization | The canonical URL drops the trailing slash (root `/` excepted); the Worker 308-redirects any trailing-slash request in a single hop, and the ASSETS binding is configured `html_handling: "drop-trailing-slash"` so static and dynamic routes answer one URL the same way | One URL per resource avoids duplicate content and split caches; 308 preserves the method and body so the rule is safe for every request; matching the Worker and asset-handler policies keeps the two serving paths consistent | Keep both forms with no redirect, force a trailing slash, or canonicalize only the dynamic routes |
| 2026-09-01 | 2 | Blanket static-asset headers | A generated `dist/client/_headers` sets `Cache-Control: public, max-age=31536000, immutable` on `/_goribu/assets/*` — the reserved namespace where Goribu writes its content-hashed client build. App files under `public/` (including any at `/assets/`) keep the platform default. The build fails closed on `public/_headers`, on anything published under `public/_goribu/`, and — via a client-bundle audit — on any file emitted under the namespace whose name carries no content hash | An immutable cache is safe only when a file's URL changes with its bytes; scoping it to `/_goribu/assets/` and auditing that every file there is fingerprinted — whatever the app's Rollup output config or another plugin does — keeps a stale file from being served under an unchanged URL; `_headers` is Cloudflare's own asset-config mechanism and needs no Worker code on the request path | Cache all of `/assets/*` immutably (unsafe: `public/assets/*` is unhashed), set cache headers from the Worker, or ship no cache policy |
| 2026-09-01 | 2 | Static and hydrated are two independent axes | **Static** describes request execution only: a route whose first response is produced at build time and served from Static Assets without invoking the Worker (what Block 2 now produces). **Browser execution is a separate axis**: the settled position is that every route hydrates (the client runtime itself lands in Block 5), so a static route with no server work and a `useState` counter is static and hydrated at once. A route-level HTML-only opt-out (static that ships no client bundle) is a real feature but post-gate | The axes must not collapse: the no-Worker cost story rests on request execution, not on whether a route ships a client bundle, and recording the position now keeps "static" from quietly coming to mean "no JavaScript" as hydration lands | Collapse the axes so "static" implies no hydration; ship the HTML-only opt-out now |
| 2026-09-01 | 2 | Build-time static output render path | Static routes are rendered at build time by running the **emitted Worker artifact in workerd**, through Wrangler's `createTestHarness`, fetching each route via the direct `getWorker()` handle (which bypasses the Static Assets front door) and writing the HTML into `dist/client`. A candidate is downgraded to Worker rendering, with a named reason, when it has no single build-time URL (a dynamic segment) or the Worker cannot render it (a non-200 or a body that fails mid-stream); only an explicit `prerender = true` that fails to render fails the build, and a rejected fetch is treated as a harness failure that fails the build. Existing client HTML whose URL a route owns fails the build | Rendering the real deployed artifact in its real runtime makes the static bytes exactly what the Worker would serve and reuses the app's own build pipeline, so no parallel render path can drift; a per-route fetch isolates each candidate so one failure downgrades alone | Render through a separate Node/SSR bundle (drifts from the artifact and cannot run Cloudflare-only modules); import the Worker bundle into Node (fails on `cloudflare:` imports); use the deprecated `unstable_dev` / `unstable_startWorker` runners |
| 2026-09-01 | 4 | Request surface | Minimal request properties plus one content-type-aware `req.body()` and a cached `req.rawBody()` | One read-and-cache path avoids stream-consumption bugs and API duplication. | Separate JSON, form, text, and raw readers plus an escape hatch |
| 2026-09-01 | 4 | Handler HTML intent | Returning HTML from a handler is `res.render(props)`, which streams the route's own default page through the document shell; there is no `res.html(string)` | `res.render` is the one HTML path — shelled, streamed, and hydratable — so a handler render uses the same streamed HTML path an implicit GET does while carrying handler-owned props, status, and headers; a raw-HTML method would ship dead, unshelled markup and split the render path. The literal-string escape hatch already exists as `res.headers({ "content-type": "text/html" }).text(html)` | Add a `res.html(string)` intent for arbitrary HTML bodies |
| 2026-09-02 | 4 | Cookie transport surface and policy | Expose the request-scoped jar as `req.cookies` with `get`/`set`/`delete`, then append pending cookies once to the final response; serialization adds no policy defaults (`SameSite=None` does not imply `Secure`), and deletion accepts only matching `path`/`domain` | Unlike v2's internal-only jar, the request surface makes cookie transport executable and observable in Block 4 while preserving the transport implementation unchanged; applications remain responsible for explicit cookie security and scope policy | Keep the jar internal and inert until Block 6's D1 session freshness uses it; add serializer security defaults or broader deletion options |
| 2026-09-02 | 4 | Folder-scoped middleware | One `_middleware` module per route directory, selected outermost-first; a default function or flat array runs left-to-right without `next`, returning `undefined` to continue or a `res.*` intent to stop. Selection happens at build time and middleware joins the existing id-keyed module map; there is no loaded-module-map or bind indirection | The runtime manifest intentionally has no filesystem paths, so the build must resolve ancestry while it still has them; emitting ready route-id selections keeps runtime composition flat, preserves one module identity scheme, and gives middleware and the eventual route one request/response pair | Runtime filesystem selection; v2's filePath-keyed loaded-module-map and bind helpers; `next`-based composition |
| 2026-09-02 | 4 | Middleware and static output | A route with selected middleware is Worker-only: automatic prerender candidates downgrade with the selected middleware files named, while `prerender = true` fails the build | Arbitrary request-time middleware cannot be proven request-independent, so serving the route from Static Assets would bypass behavior the route owns; Worker generation and static planning share one build-time middleware-selection helper so the two decisions cannot drift | Prerender the middleware-produced build response anyway; independently derive middleware presence in each build step |
| 2026-09-02 | 4 | Request error boundary | Catch request-path throws at the app boundary; branded `HttpError` becomes its safe 4xx plain-text response in both modes, while other throws disclose their stack in development or become a production `_500` rendered with a logged correlation ID. Error renderers receive only `URL.pathname`, never query data | Client-safe framework errors should remain actionable, local failures should teach, and production failures must be correlatable without exposing raw errors or query-string secrets; keeping the boundary inside `fetch` leaves build/construction failures loud | Let request throws reject; render every error through `_500`; disclose production errors; pass the full request URL |
| 2026-09-02 | 4 | Runtime mode source | Derive development/production from Vite's `serve`/`build` command, bake it into the generated Worker, and default to production when absent | One generated runtime boundary must disclose locally and stay opaque in production; a production default fails safe when the build signal is unavailable | Runtime environment inference; application configuration; default development |
| 2026-09-02 | 4 | HttpError brand identity | Brand framework `HttpError`s with a module-private `WeakSet` (identity), not a private Symbol property; `isHttpError` classifies by `WeakSet.has` behind a typeof guard and reads no properties of the value. Supersedes the byte-identical `http-error.js` ported in the request-surface substep | The error boundary must classify arbitrary thrown values, including a hostile `Proxy` whose `get` trap throws — a property read (`value[HTTP_ERROR]`) could throw during classification and escape the boundary it feeds; a `WeakSet` identity check invokes no user code and cannot be forged. v2 retains the Symbol-property brand | Keep v2's Symbol-property brand; wrap every classification read in try/catch |
| 2026-09-02 | 4 | Worker runtime request contract | `fetch(request, env, ctx)` is the Worker contract; routes and middleware receive the raw request-scoped bindings object as `req.env` and only the eagerly bound `req.waitUntil` capability, while `ctx` and `passThroughOnException` stay private. `createApp()` remains construction-time application config only | Bindings and execution context belong to each Worker invocation, and exposing only the capability routes need prevents the raw platform context from becoming public API | Expose `ctx` directly; put `env` on `createApp()` |
| 2026-09-02 | 4 | Server-only client boundary | Files named `.server.*` may be imported by route handlers but must never reach the client bundle; a Vite pre-plugin enforces this only in the `client` environment through a `resolveId` guard plus a final chunk-module audit. Block 4 ships and tests the convention and mechanism; Block 5 owns the virtual client-route entries that make route pages browser-reachable | Establishing the fail-closed boundary before hydration adds route code to the browser graph prevents accidental server leaks without pulling Block 5 machinery forward; environment-name gating keeps legitimate Worker imports untouched under Vite's environments API | Defer the entire boundary to Block 5; gate on the legacy `ssr` resolution flag; port virtual client-route entries now |
| 2026-09-02 | 4 | Server-only module placement | `.server.*` modules live outside `src/routes/` and are imported by handlers from there; the route scanner reserves only the `_` prefix, not the `.server.*` suffix, so a `.server.*` file placed under `src/routes/` is still treated as a route and fails route analysis | The `.server.*` boundary this substep ships is the client-bundle guard, not a routing convention; colocating server modules inside the route tree would require the scanner to reserve the suffix — a discovery-rules change with no current consumer, matching v2, which never route-scans its `.server.*` files | Reserve `.server.*` in route discovery now so server modules can sit beside the routes that use them |
| 2026-09-02 | 2 | Immutable asset hash audit boundary | Recognize Vite's generated hash as the final eight base64url characters after a hyphen; anchor on the known length because `-` is valid inside the hash, retain the entropy check, and fail closed if a future Vite changes its default hash length | The first dynamic client chunks exposed that splitting on the final hyphen rejects valid hashes containing `-`; pinning the audit to the build engine's actual default accepts Vite output without weakening rejection of fixed or dictionary-tail names | Split on the final hyphen; accept any eight-character suffix; disable the emitted-bundle audit |
| 2026-09-02 | 5 | Initial browser boundary in custom Documents | Export `<ClientEntry>` from `goribu`; both the framework default and a custom Document render it once after `#root`, where it emits inert route data, inert props, then the client module entry. Its explicit `/src/client-entry.js` source is development-only until Block 5's static-hydration substep adds build-resolved hashed assets and module preloads | Hydration bootstrap is body-side browser-runtime ownership, not a metadata/head helper; one public component preserves custom Document placement, the inert-JSON protocol, and the same boundary for framework and app Documents without importing package internals | Inject scripts only into the default Document; make apps import internal render-context components; replace inert JSON with a bootstrap global; defer the public component to metadata work |
| 2026-09-02 | 5 | Worker/browser navigation protocol | Reserve `/_goribu/worker-nav` for same-origin application GETs and return a kind-tagged `render`/`redirect`/`reload` JSON envelope with `Cache-Control: no-store`; browser fetch uses `redirect: "manual"`, uncertainty hard-loads the document, and manual scroll restoration stores coordinates per history entry while preserving application state. Route metadata is deliberately absent until its later Block 5 substep, and the copied Form bridges remain dormant until substep 4 | An explicit protocol lets hydrated pages validate and load the next route before committing UI/history, while every unsupported or stale state falls back to normal document semantics; keeping metadata out and Form seams dormant preserves one-substep-at-a-time ownership | Fetch route HTML and morph it; follow wire redirects automatically; fail open after partial client commits; pull metadata or Form behavior into this substep |
| 2026-09-02 | 5 | Enhanced form negotiation | An enhanced `<Form>` mutation posts to its real route URL with `Accept: application/vnd.goribu.form+json`; the route runs through ordinary routing, middleware, handlers, and cookies, then serializes its `res.*` result to a typed JSON envelope (`json`/`invalid`/`redirect`/`render`) with `Cache-Control: no-store` and `Vary: Accept`, stripping representation headers while keeping application headers and `Set-Cookie`. A form request whose result is not a form kind (e.g. `res.text()`) falls through to its ordinary representation; the browser then reads a non-form content type and does a full document load | Keying enhancement on `Accept` lets one handler serve both a native submit (HTML) and a hydrated submit (envelope) with no branching in application code, and reusing the existing dispatch means forms inherit middleware, cookies, and error boundaries unchanged | A dedicated form endpoint or reserved path; a request header flag instead of `Accept`; a bespoke form dispatch separate from route handlers |
| 2026-09-02 | 5 | Same-page form render safety | `res.render()` on an enhanced form request is allowed only when a parseable same-origin `Referer` pathname equals the action pathname (the form's own page); otherwise it throws and teaches `res.redirect()`/`res.json()`. A native (unnegotiated) submit has no such restriction, because the browser has moved the URL to the action | Rendering another route's page in place while the URL bar shows the form's page is a broken state; restricting enhanced in-place render to the same path keeps content and URL consistent, while the native full-page submit is already consistent by construction | Allow any in-place render and update the URL to the action; forbid form renders entirely and require redirect |
| 2026-09-02 | 5 | Pre-hydration form contract | `<Form>` is strictly progressive enhancement: it renders a real `<form>` with resolved `action`/`method`, so a submit before its `onSubmit` attaches is an ordinary native full-page submission answered in document mode as HTML. A submit after the handler attaches but before the navigation runtime installs fails closed to a full document load rather than committing partial client state. Both are tested | Forms are hydrated by design, so the racing-submit window must have a defined, safe outcome; anchoring the baseline on native submission means the worst case is a full page load, never a broken or swallowed submit | Disable the form until hydration completes; queue the submit and replay it after bootstrap; leave the pre-hydration behavior undefined |
| 2026-09-03 | 5 | Form method and pre-hydration representation correction | Supersedes the earlier enhanced-negotiation row's blanket “native submit (HTML)” phrase and the pre-hydration row's blanket HTML wording: public `<Form>` supports only native `GET` and `POST`; enhanced GET uses navigation, while enhanced document negotiation is POST-only. Goribu owns multipart encoding for native POST. Before hydration, results keep their ordinary server representations: `res.render()` streams HTML, `res.redirect()` is a wire redirect, and `res.json()` / `res.invalid()` are full-page JSON responses. Enhanced validation and in-place errors require hydration | Native submission must honestly expose the existing response intent instead of inventing an SSR validation context; limiting enhancement to the two native form methods keeps the browser baseline and enhanced path aligned | Describe every native POST result as HTML; build a second server-side validation context; negotiate form envelopes for GET or non-native mutation methods |
| 2026-09-03 | 5 | Production client asset delivery | Build the client environment before every Worker environment, capture its hashed entry and per-page chunk graph in a Vite plugin instance shared only during builds, and expose the captured manifest plus normalized Vite base to the generated Worker through `virtual:goribu/client-assets`. Production loading fails closed if capture has not completed; development exports a null manifest and keeps the explicit source fallback | The deployed Worker and build-time prerenderer both need the final client graph, which exists only after the client build. Cloudflare's default orchestration is Worker-first, so ordering must be owned rather than assumed; a virtual module keeps generated data inside Vite's graph and cannot consume stale state from an earlier build | Write a manifest file for the Worker to import; let production silently retain `/src/client-entry.js`; rely on Cloudflare's default environment order |
| 2026-09-03 | 5 | Route metadata and managed head ownership | A route exports a static object or synchronous `meta({ props, url })`; Goribu strictly normalizes the result before streaming, renders one marked route-owned head set through `Document({ children, head, nonce })`, and atomically replaces only those marked nodes after navigation or same-page form rendering | Metadata remains a pure projection of the already loaded render data, failures reach the ordinary request boundary before bytes commit, and application-owned viewport/icon/head nodes survive browser navigation | Async metadata or request/env access; a public `<Head>` component; arbitrary React nodes; precedence rules between duplicate semantic forms |
| 2026-09-03 | 5 | Document assets, nonce, and response policy | Export zero-prop `<Stylesheet />` for production graph CSS and keep `<ClientEntry>` body-side; each request mints one cryptographic nonce shared by `responseHeaders({ request, env, mode, nonce })` and, for Worker-owned document renders, `Document`, inert data scripts, the client module, and React streaming scripts. A route selected as a static candidate omits the HTML nonce so repeated renders remain byte-identical; Static Assets cannot promise a per-request value. Global headers are synchronous defaults, with unsafe blanket fields rejected and protocol representation fields protected | CSS placement stays explicit while asset identity stays build-owned; one nonce connects dynamic CSP policy to every script; deterministic static HTML preserves the emitted-Worker prerender invariant; one callback covers CSP/CORS/HSTS without letting global policy override the response that owns transport or negotiated representation | Author-supplied stylesheet URLs; CSS emitted by `<ClientEntry>`; put a reusable build-time nonce in static HTML; static header objects; route middleware wrapping every response; framework CSP defaults |
| 2026-09-03 | 5 | Development graph stylesheet delivery | In production `<Stylesheet />` emits the hashed CSS captured from the client graph; in development it emits nothing because Vite loads and injects CSS through the application client entry module | Goribu 3 uses Vite's live client module graph directly in development, so v2's separately watched `/_goribu/client/styles.css` snapshot server does not exist and porting that endpoint would duplicate the active dev pipeline | Port v2's separate audited development client builder and aggregate stylesheet endpoint; require an application-owned development stylesheet link |
| 2026-09-03 | 5 | Static response-header boundary | `responseHeaders` applies only when the Worker executes; routes served from Static Assets receive only Goribu's generated immutable asset rule, and app-authored `public/_headers` remains rejected. Static routes therefore cannot currently receive application-defined headers such as a nonce-free CSP, and Block 5 documentation must state that limitation rather than imply the Worker policy covers them | A request-, binding-, and nonce-aware callback cannot run on a request that bypasses the Worker, while freezing one build-time result into asset rules would misrepresent dynamic policy. | 2026-09-03 | 5 | Public browser environment | Reserve the exact Vite `PUBLIC_` env prefix and expose those string values through `import.meta.env`, rejecting user config or plugins that broaden `envPrefix` | Production builds and Vite development share mode-aware environment loading while unprefixed secrets and legacy `VITE_*` values stay outside Goribu's browser contract | Vite's default `VITE_` prefix; configurable prefixes; `process.env`; a runtime environment export; serialize environment values through application configuration |
| 2026-09-03 | 6 | Deploy safety and D1 inspection | `goribu check` is a read-only plan: load the canonical config, use Goribu's pinned Wrangler to run `d1 list --json`, and print the production target, existing/missing/create state, `DB` mapping, and cost warning with an explicit no-changes footer; skip remote inspection when no database is declared | Reuses Wrangler's authentication and account selection without owning credentials, keeps planning visibly separate from `goribu deploy` mutation, and introduces only the D1-shaped case currently in hand | Call Cloudflare's API directly; make deploy print its own implicit preview; build a generic multi-resource planner before KV exists |
| 2026-09-03 | 6 | D1 provisioning and binding ownership | `goribu deploy` first checks binding ownership and completes the production build, then resolves credentials through pinned Wrangler, creates D1 through Cloudflare's API with the intended replication mode in the same request or reconciles an explicit `replication` policy on an existing database, puts the resolved UUID into the emitted `DB` binding, and hands the finished output to Wrangler. | 2026-09-04 | 5 | Public route chunk names | Name every generated route entry `client-route-[content hash].js` while retaining its absolute source path only inside the virtual module ID used during the build | Rollup's default name was derived from that virtual ID and exposed an encoded developer filesystem path in deployed URLs.
