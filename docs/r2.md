# R2

Goribu 0.9.0 adds managed R2, including bucket configuration,
request APIs, signed downloads, deployment provisioning, direct-upload CORS,
and the browser upload helpers. `goribu check` reports the deployment plan
without making changes. Core upload and download flows have passed live account
and browser verification. See the [release guide](releasing.md) for package
preparation, publication, and app upgrades.

## Configuration

Declare buckets in `goribu.config.js`:

```js
import { defineConfig } from "goribu/server";

export default defineConfig({
  name: "my-app",
  compatibilityDate: "2026-09-01",
  r2: {
    name: "my-app-media",
    domain: "media.example.com",
    private: { name: "my-app-files" },
    jurisdiction: "eu",
  },
});
```

Goribu supports one default bucket and an optional second private bucket.

| Configuration | Generated bindings |
| --- | --- |
| `r2: { name: "my-app-files" }` | `R2` for a private default bucket |
| `r2: { name: "my-app-media", domain: "media.example.com" }` | `R2` for the bucket intended for public files |
| The example above | `R2` and `R2_PRIVATE`, both with EU jurisdiction |

Names must contain 3 to 63 lowercase letters, digits, or hyphens, and start and
end with a letter or digit. The two buckets must have different names.

`domain` is a bare hostname with at least two labels, such as `media.example.com`.
Hostnames are normalized to lowercase. Single-label names such as `localhost`,
schemes, paths, ports, IP addresses, trailing dots, and `r2.dev` hosts are rejected.
`goribu deploy` connects the hostname and makes the default bucket publicly
accessible through it. Development and standalone builds do not connect domains.

`private` accepts only `name` and requires a `domain` on the default bucket.
For one private bucket, use `r2: { name: "my-app-files" }`.

Omit `jurisdiction` for the default jurisdiction, or set it to `"eu"` for both
buckets. Unknown fields are rejected. `defineConfig()` takes an immutable
snapshot, including the nested private-bucket declaration.

Goribu writes the bindings into its generated `goribu.wrangler.jsonc`. When
`r2` is configured, handwritten `r2_buckets` declarations in `wrangler.json`,
`wrangler.jsonc`, or `wrangler.toml`, including named environments, fail during
development, build, and deployment setup. Configure at most two buckets through
`r2` in `goribu.config.js`.

Development uses local buckets and needs no R2 credentials. The generated
configuration uses bucket names directly; local data persists across development
server restarts. Production builds retain the same names and jurisdiction.
To delete local objects, such as test uploads, run `goribu local:clear r2`,
optionally with `--prefix avatars/`; see [cli.md](./cli.md#goribu-localclear).

For an R2 app, `goribu dev` creates `.goribu/dev-secret` on first serve and reuses
it across restarts. It supplies this generated value as `GORIBU_SECRET` to the
local Worker only. Cloudflare keeps loading root `.env`, `.env.local`, or
`.dev.vars` normally; an app-defined `GORIBU_SECRET` takes precedence. The
generated secret is absent from `goribu.wrangler.jsonc` and production output.
Removing `.goribu/dev-secret` regenerates it on the next serve and invalidates
local signed links that used it.

## Production buckets and checks

`goribu check` inspects the configured buckets in the selected Cloudflare account
and reports which exist, which deploy would create, their bindings and
jurisdiction, the domain connection, and whether the signing secret exists. It
makes no changes. `goribu deploy` repeats this inspection after
building and validating any production secrets file, then creates only missing
buckets. A standalone build does not create or inspect production resources.

Inspection uses Wrangler's authenticated account and credentials. It needs R2
read access and Workers Scripts Read permission to compare the deployed Worker's
R2 bindings; creation also needs R2 write access. EU configuration applies to
every bucket request. An unrecognized response or permission failure stops the
operation rather than treating a resource as missing.
If you use a scoped API token, include Workers Scripts Read as well as the R2
permissions for both `goribu check` and `goribu deploy`.

When `r2.domain` is set, inspection also needs Zone Read. Goribu finds the most
specific matching active zone in the same account as the buckets, before any
resource changes. A missing, inaccessible, inactive, or mismatched zone blocks
deployment with a repair instruction. It attaches a missing domain after bucket
creation, using TLS 1.2 as the minimum for new connections. Existing enabled
connections keep their settings. If the configured domain is connected but
disabled, enable it in Cloudflare's R2 bucket settings or change `r2.domain`;
Goribu does not overwrite that setting. It does not reassign a hostname already
in use elsewhere. DNS and certificate activation can take time after attachment;
inspect the domain status in Cloudflare before expecting the public URL to work.

If the deployed Worker already uses `R2` or `R2_PRIVATE` for a secret, check and
deploy stop: Wrangler preserves deployed secrets. Remove or rename the entry in
`.env.production` if present, then run the printed
`pnpm exec goribu wrangler secret delete R2` or `… secret delete R2_PRIVATE`
command and retry deployment. The command names the inspected Worker and runs
with the account deploy uses; secrets have no jurisdiction flag. Goribu never
reads or deletes the secret itself.

Other existing binding types produce a warning: deployment replaces them with
the configured managed bucket, or removes `R2_PRIVATE` if no private bucket is
configured. Update app code that used the previous binding. Goribu does not ask
Wrangler to retain non-secret bindings.

Changing a bucket name or adding/removing EU jurisdiction warns about the switch
from the deployed binding. Goribu does not migrate objects, so stored keys may
no longer resolve in the new bucket. Review the warning and migrate data before
switching. Removing the private-bucket declaration leaves that bucket and its
objects in Cloudflare.

A private bucket with public `r2.dev` access or any enabled custom domain blocks
both check and deploy. This applies to the default bucket when `r2.domain` is
absent and to `R2_PRIVATE`. The error prints the command to disable public
`r2.dev` access or remove the domain, including `-J eu` when needed. Both buckets
are inspected before any bucket is created, and an unsafe R2 plan stops
deployment before D1/KV provisioning or migrations. Disabled custom domains on
private buckets do not block deployment.

Removing or changing `r2.domain` does not disconnect an existing custom domain.
Check and deploy warn about extra enabled domains on a bucket still configured
as public, and block if the bucket is now configured as private. They print the
command to remove each domain yourself. Omitting a domain from configuration
does not make the bucket private.

Provisioning never deletes buckets or objects, disconnects domains, or enables
`r2.dev`. If creation fails partway through, buckets already created remain;
rerun `goribu check` before retrying deployment.

## Production signing secret

For an existing Worker, Goribu checks secret names with `wrangler secret list`.
It never reads secret values or parses app-authored env files. Before the final
upload, after provisioning and migrations, it rechecks the Worker and secret
names. If `GORIBU_SECRET` is missing, it generates 32 random bytes as base64url
and sends the value directly to `wrangler secret put GORIBU_SECRET` through stdin.
The generated value is not written to a local file or printed. Secret-command
diagnostics and Wrangler disk logging are suppressed; failure reports login and
permission repair instructions without raw command output. Creation requires Workers Scripts write
access. Existing text secrets are reused.

For a first deployment, Wrangler creates a draft Worker to hold the secret before
the final upload. Check reports this step. A later failure leaves the draft and
secret in place so a retry can reuse them; Goribu performs no deletion or rollback.

`.env.production` still goes unchanged to Wrangler on final upload. If it
contains `GORIBU_SECRET`, that app-provided value wins, including over a secret
just generated. Goribu cannot know its presence without parsing the file, so
the read-only plan describes platform state. A standalone build does not create
a production secret or read credentials.

## Direct-upload deployment

Only buckets used by `direct: true` fields need upload CORS and R2 credentials.
`goribu check` uses the last build's upload metadata and prints its build time;
it does not build or inspect later source edits. If no metadata is available,
it prints "run goribu build first" for CORS and R2 key checks while continuing
bucket, domain and signing-secret inspection. Older metadata without an embedded
build time uses its file timestamp. Invalid metadata requires a rebuild.
`goribu deploy` always builds fresh and checks that output before provisioning.

Goribu plans origins from the Worker's `workers.dev` address (unless
`workersDev: false`), Worker custom domains, and exact-host Worker routes in the selected account.
When [application `domain`](deploy.md#custom-domain) is configured, its planned
HTTPS origin is included before attachment and labeled "connected by this
deploy" when new.
Path wildcards such as `app.example.com/*` are supported. Hostname wildcards
such as `*.example.com/*` warn and are skipped. Routes without a scheme allow
both HTTP and HTTPS origins; explicit schemes stay restricted to that scheme.
Allowing an HTTP origin permits uploads from a plaintext page; use an explicit
HTTPS route if the app should upload only from HTTPS pages.
Preview URLs and the bucket's media domain are not app origins. There is no
separate origins configuration.

Unless the app sets [`workersDev: false`](deploy.md#workersdev-address), Goribu
includes `https://<name>.<account-subdomain>.workers.dev` from the account
subdomain. Before the Worker exists, it labels this origin "expected after first
deploy". When an existing Worker has workers.dev disabled, including a draft
created during secret setup, it labels the origin "enabled by this deploy".
Goribu's generated configuration sets `workers_dev` from `workersDev`, so each
deployment enables or disables this address to match. There is no manual
enablement step. If the account has no subdomain, register one in Cloudflare
Workers & Pages first; Goribu does not register it automatically. With
`workersDev: false`, the workers.dev origin is left out and removed from
`goribu-uploads` on the next deploy.

Origin discovery needs Workers Scripts Read, Zone Read, and Workers Routes Read
for the account's zones. Goribu follows all pages of domains, zones and routes;
there is no 50-item account limit. The documented route-list API is zone-scoped,
so route inspection still needs permission on every zone returned for the account,
including zones without this app's routes. Zones hidden by token scope cannot
be discovered. Permission errors and incomplete, repeated or inconsistent pages
stop the operation. Unless `workersDev: false`, direct uploads require an
account workers.dev subdomain; its absence stops deployment before provisioning,
even if a custom domain is configured, because the deployment enables workers.dev.

**Redeploy after adding or changing an application domain or route.** CORS is
updated during deployment, so a hostname added later is not automatically allowed.
Check reports Cloudflare hostnames, the configured app domain, and any workers.dev
address that deployment will enable. Check itself makes no changes.

On each direct-upload bucket, deploy upserts `goribu-uploads` with method `PUT`,
a 3600-second preflight cache, and allowed headers `content-type`, `cache-control`,
`if-none-match`, and `x-amz-meta-goribu-upload`. It preserves unrelated rules and
leaves buckets without direct fields untouched, including any earlier upload
rule. It rereads before writing and verifies afterward. Avoid concurrent CORS
edits in Cloudflare during deploy: the API replaces the whole list and offers
no atomic merge.

Direct uploads need an R2 API token, stored as the Worker secrets
`R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`. You don't need to set them up
before deploying. When either is missing, check lists it, and `goribu deploy`
run from a terminal sets them up on the way:

1. Deploy creates the upload buckets, runs migrations and creates
   `GORIBU_SECRET`, as usual.
2. It prints a link to the account's R2 API tokens page and the buckets to
   scope a new token to, with Object Read & Write permission, including their
   jurisdiction. The buckets exist at this point, so the token can be scoped to
   them.
3. For each missing name, Wrangler asks for the value with a hidden prompt.
   Paste the token's Access Key ID and Secret Access Key. Goribu runs its bundled
   Wrangler for this, pinned to the deploy account, and never sees the values.
4. Deploy confirms both names with `wrangler secret list`, then uploads the
   Worker.

If you cancel a prompt, deploy stops before the Worker upload. Run it again to
be asked for whatever is still missing; created buckets and the draft Worker are
reused. A deploy without a terminal, such as in CI, stops before any change and
says to run `goribu deploy` once from a terminal. Later deploys reuse the stored
secrets.

Only names returned by `wrangler secret list` satisfy this check. Goribu never
reads credential values or app-authored env files, even to extract names, so
keys declared only in `.env.production` still lead to the prompt. That file
goes unchanged to Wrangler at final upload, so it can rotate the values later.
A name check cannot prove that a credential is valid or has access to a bucket. Dev needs no R2 API token.

## The request API

Handlers and middleware receive `req.r2`. It exposes the native Workers R2
methods: `head`, `get`, `put`, `delete`, `list`, `createMultipartUpload`, and
`resumeMultipartUpload`. Their options, streaming bodies, conditional results,
errors, and multipart objects pass through. In particular,
`resumeMultipartUpload()` returns its multipart object synchronously. See the
[Cloudflare Workers R2 API reference](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)
for those contracts.

```js
export async function GET(req, res) {
  const object = await req.r2.get("config/homepage.json");
  if (!object) return res.notFound();
  return res.json(await object.json());
}
```

`put(key, value, options?)` adds one convenience: a `File` or `Blob` with a
nonempty `type` supplies `httpMetadata.contentType` when none is specified.
An explicit content type wins, whether metadata is a plain object or `Headers`.
Goribu preserves the caller's options and headers without modifying them.

```js
await req.r2.put("exports/latest.csv", csvBlob);
await req.r2.put("exports/latest.csv", csvBlob, {
  httpMetadata: { contentType: "text/csv", cacheControl: "no-cache" },
});
```

With a second bucket configured, use `req.r2.private` for the same native methods.
It has no `url()` method. Without a domain, the default `req.r2` is itself the
private bucket; a second bucket is unnecessary.

`req.r2` always exists, but operations throw an actionable configuration error
when no bucket is declared. Async methods return rejected promises, including
for configuration and binding errors; `url()`, `resumeMultipartUpload()`, and
accessing an unconfigured `req.r2.private` throw synchronously. Each binding
resolves only on its first storage operation in a request.
Unused R2 configuration therefore does not require a binding at runtime.

## Public URLs

Store object keys in your database and derive URLs when needed:

```js
const url = req.r2.url("avatars/a b.png");
// Production: https://media.example.com/avatars/a%20b.png
// Development: /_goribu/r2/public/avatars/a%20b.png
```

`url(key)` is synchronous and needs only configuration, so it works during
prerendering without accessing storage. It requires `r2.domain` and does not
check whether the object or production domain exists. Each path segment is
percent-encoded, preserving slashes. Empty keys, invalid Unicode, and `.` or
`..` path segments are rejected; browsers would normalize the latter into a
different path.

In development, the internal public-file endpoint streams from the default
local bucket, with stored HTTP metadata, ETag revalidation, and HEAD support.
It uses `Cache-Control: no-cache` so edits are revalidated. It cannot serve the
private bucket or a default bucket without `r2.domain`. This helper is removed
from production builds, where `/_goribu/r2/public/*` returns 404; production
public files must be served by the configured custom domain.

Files served on the app's own origin—both this dev endpoint and Worker-served
signed downloads—always receive `Content-Security-Policy: sandbox` and
`X-Content-Type-Options: nosniff`. These fixed headers prevent uploaded HTML or
SVG documents from running scripts with the app's origin privileges. They apply
to partial, conditional, and error responses too, and override app-wide header
defaults. Stored content types are preserved; these endpoints do not support
serving active application pages. Public custom-domain and S3 responses are
served separately and do not pass through this header policy.

## Signed downloads

Both `req.r2.signedUrl(key, options?)` and `req.r2.private.signedUrl(key, options?)`
return a promise for a time-limited GET URL. Check the current user's authorization
in your handler **before** creating the link: anyone holding the URL can use it
until it expires, without passing through route middleware again.

```js
// After checking that the current user may read this invoice:
const downloadUrl = await req.r2.private.signedUrl(invoice.fileKey, {
  expiresIn: 600,
  download: "invoice.pdf",
});
return res.json({ downloadUrl });
```

`expiresIn` defaults to 900 seconds and accepts integers from 1 to 604800.
`download` requests an attachment filename; it must contain 1 to 255 characters
without slashes or control characters. Unicode names use an encoded filename
alongside an ASCII fallback. Keys must be valid Unicode, at most 1024 UTF-8 bytes,
and have no `.` or `..` segments.

For immutable images or other files whose bytes never change under the same key,
opt into reusable links and private browser caching:

```js
// Authorize this user first. Replacing the image must create a new object key.
const imageUrl = await req.r2.private.signedUrl(image.fileKey, {
  expiresIn: 604800,
  immutable: true,
});
```

`immutable` defaults to `false`. Setting it to `true` promises fixed contents and
permits private browser caching until link expiry. URLs are identical within
windows of `max(1, floor(expiresIn / 2))` seconds for the same key, bucket,
options, origin (Worker links), and signing credentials. A link has at least half
its requested lifetime remaining when issued. A seven-day lifetime rotates URLs
about every 3.5 days; crossing a window causes a new cache entry, and browsers may
evict entries sooner. Ordinary links keep their full lifetime from issuance.

Worker responses bound `max-age` by remaining link validity and add `immutable`.
S3 links sign `response-cache-control=private, immutable` and an absolute
`response-expires` date, preserving URL stability while requesting freshness
only until expiry. These headers permit browser caching, not shared CDN caching.
Expiry does not erase downloaded bytes. Logout, permission changes, deletion,
and secret rotation cannot revoke bytes already cached; use the default behavior
when this caching contract is unsuitable. Signed URLs remain bearer credentials.

In production, supplying both `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` in
the Worker environment selects an S3 SigV4 URL. `goribu deploy` supplies
the internal `GORIBU_R2_ACCOUNT_ID` Worker variable from the authenticated account
it selected for deployment. The shell's `CLOUDFLARE_ACCOUNT_ID` remains an input
for account selection. Standalone builds require no account credentials.
EU buckets use the account's
`.eu.r2.cloudflarestorage.com` endpoint. A partial credential pair fails with a
repair instruction. Credentials are used only inside the Worker, never sent to
the browser as raw values. The resulting signed URL is itself a credential.

Enabling direct uploads requires these credentials, so it also selects direct
S3 downloads in production. Development continues to use Worker downloads.

Without those keys, and always in development, the URL targets
`/_goribu/r2/file?t=…` on the request's origin. It requires `GORIBU_SECRET` in
the Worker environment. This endpoint verifies the token's purpose, signature,
expiry, and bucket before accessing storage. It streams GET responses, supports
HEAD and single byte ranges, and answers ETag revalidation with 304. Failed
`If-Match`/`If-Unmodified-Since` preconditions return 412; unsatisfiable ranges
return 416. Responses use `Cache-Control: private, max-age=0`.
Worker-served files use `Content-Security-Policy: sandbox` and
`X-Content-Type-Options: nosniff`, so uploaded HTML or SVG cannot run scripts as
the app.
Inline PDF viewing and attachment downloads with these headers were verified
in Chrome 154 on macOS.

The prerender harness rejects `signedUrl()` calls: an expiring URL must not be
frozen into static HTML. Automatic candidates fall back to Worker rendering.
For an explicitly prerendered route, remove `prerender = true` or set
`prerender = false`. Rotating `GORIBU_SECRET` invalidates existing Worker-served
links; S3 links use the separate R2 credentials.


## Upload policies

Goribu validates a route's `uploads` export during `goribu build` and when
serving the app in development. Use `<FileUpload>` inside a `<Form>` to keep a
file in R2, or `upload()` for a custom UI outside a form.

Each field requires a non-empty `accept` array of MIME types and a positive
integer `maxBytes`. Specific types and wildcards such as `image/*` are accepted;
`*/*` is rejected. The maximum is 100,000,000 bytes through the Worker, or
5,000,000,000 with `direct: true`. Optional `private: true` stores the field in the
second bucket, `r2.private`, and requires it. It does not make a field private
on its own: with a single bucket and no `domain`, every upload is already
private, so leave `private` out.
An optional synchronous `key({ req, file, ext })` function chooses the object key.
It runs after middleware with the same request. `file.name` is the basename
without control characters, capped at 255 characters; `ext` is a lowercase
alphanumeric extension including its dot, at most 10 characters, or empty.
Keys must be non-empty, valid Unicode, at most 1,024 UTF-8 bytes, without a
leading `/` or `.` or `..` path segments. Return a new key for every upload,
for example `avatars/${req.params.id}/${crypto.randomUUID()}${ext}`. A fixed key
such as `avatars/${req.params.id}.png` makes the second upload fail with 409
because uploads refuse to overwrite existing objects. To replace an avatar,
upload under a fresh key, save the verified new key, then delete the old object.
Unknown options and getters are rejected. TypeScript apps can use
`Record<string, UploadPolicy>` with `UploadPolicy` imported from `goribu/server`.

A route exporting `uploads` must also export `POST`, `PUT`, or `PATCH` to receive
the upload ref. That route runs on the Worker; `prerender = true` fails the build.
A static page can instead use `<Form method="post" action="/profile/save">`,
with the policy and receiving handler on `/profile/save`. Loading the static
page still bypasses the Worker.

Only `accept` and `maxBytes` are included in the current route's HTML hydration
and navigation payloads. A static page targeting another action route does not
receive that route's policy hints, so its file picker has no policy-derived filter
or instant size check. The upload-start response will not supply or cache hints;
validation on the server remains authoritative.
Policy key functions stay in the server bundle. Client source maps retain
mappings but exclude embedded source text, which would otherwise expose the
server code colocated with page components.

### Uploading from a form

Declare the policy on the route that receives the form, then read the verified
file from `req.body()`:

```jsx
import { Form, FileUpload } from "goribu";

export const uploads = {
  avatar: { accept: ["image/*"], maxBytes: 5_000_000 },
};

export async function POST(req, res) {
  const { avatar } = await req.body();
  if (!avatar) return res.invalid({ avatar: "Upload an image." });
  // Persist avatar.key with the application's record here.
  return res.json({ key: avatar.key });
}

export default function Profile() {
  return (
    <Form method="post">
      {({ pending, uploading, errors }) => <>
        <FileUpload name="avatar" />
        {errors?.avatar && <p>{errors.avatar}</p>}
        <button disabled={pending}>{pending ? "Saving…" : "Save"}</button>
        {uploading && <p>Your file is uploading.</p>}
      </>}
    </Form>
  );
}
```

`<FileUpload>` takes only `name` and an optional render function as its child.
The default UI is a visible file picker and status/error text. Picking starts
an upload immediately. A new pick cancels the previous request, discards its
ref, and starts again. Each field holds one file; several differently named
fields can share a form.

For a custom chooser, use the basic render values:

```jsx
<FileUpload name="avatar">
  {({ file, status, errorMessage, showPicker }) => <>
    <button type="button" onClick={showPicker}>
      {file ? file.name : "Choose image"}
    </button>
    {status === "uploading" && <span>Uploading…</span>}
    {errorMessage && <p>{errorMessage}</p>}
  </>}
</FileUpload>
```

`file` is a `File` or `null`; `status` is `idle`, `uploading`, `done`, or `error`.
`errorMessage` is user-ready text on failure and otherwise `null`. Call
`showPicker()` from a user gesture, such as a button click. With a render child,
Goribu's picker is hidden.

For previews and drag-and-drop, add `previewUrl` and `dropProps`:

```jsx
<FileUpload name="avatar">
  {({ previewUrl, dropProps, showPicker, errorMessage }) => (
    <div {...dropProps}>
      {previewUrl && <img src={previewUrl} alt="Selected image" />}
      <button type="button" onClick={showPicker}>Choose or drop an image</button>
      {errorMessage && <p>{errorMessage}</p>}
    </div>
  )}
</FileUpload>
```

`previewUrl` is a local blob URL for images, and `null` for other files. Goribu
revokes it on replacement, form reset, action change, or unmount. Unmount also
aborts both the upload-start request and the byte transfer. Reset clears the
selection and ref; it does not delete an uploaded object.

Form's `uploading` is true while any field is uploading. `pending` still means a
submission is in progress: submitting starts pending immediately, waits for all
uploads (including a replacement pick), then adds the current refs to the controls captured when submission started.
Disabling controls while pending does not drop those values. A failed
field is absent; the handler should return `res.invalid()` if it is required.
The unnamed picker does not trigger multipart encoding: enhanced submissions
stay URL-encoded unless the form also has a regular enabled named file input.
Upload controls require hydration. Use a plain file input for files you intend
to process and discard instead of keeping them in R2.

### Uploading outside a form

`upload(file, { action, name, signal? })` from `goribu` starts an upload and
resolves to a signed ref. `action` must be a same-origin HTTP(S) route that
declares `uploads[name]`. Send the ref to that route to obtain a verified value:

```js
import { upload, UploadError } from "goribu";

async function saveDroppedImage(file, signal) {
  try {
    const ref = await upload(file, { action: "/profile/save", name: "avatar", signal });
    return await fetch("/profile/save", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ avatar: ref }),
      signal,
    });
  } catch (error) {
    if (signal?.aborted) return;
    if (error instanceof UploadError) {
      // Display error.message in your UI.
    }
    throw error;
  }
}
```

Call this from your drop, paste, or file-selection handler. There is no automatic
retry: call `upload()` again to obtain a fresh target. Start requests carry
same-origin credentials for middleware authorization; PUTs carry the signed
headers and file bytes without cookies. The browser sets Content-Length.

`UploadError.code` is `type`, `size`, `forbidden`, `network`, `expired`, or
`server`, with a safe user-ready `message` without a `[Goribu]` prefix. Size
refusals from the action include its `maxBytes` limit, including for cross-route forms and
`upload()`. This error detail does not supply or cache picker hints. Transfer
size mismatches without a policy limit retain the generic size message.
Cancellation rejects with a `network` UploadError; check your signal's `aborted` flag to suppress cancellation UI. A refused or expired signed
PUT never retries or falls back to an overwrite. `<FileUpload>` suppresses errors
from canceled attempts automatically.

### Transfer and verification

An upload start runs the action route's middleware before Goribu validates the
declared file size and MIME type. The receiving POST, PUT or PATCH handler runs
later, when the form submits its ref. Protect the action with middleware that
checks authorization; the transfer URL and ref are bearer credentials.

Transfer URLs expire after 60 seconds. A ref can be submitted for one hour and
binds the action's route pattern, field, bucket, key, size, content type and a
random upload ID. The stored object's upload ID must match the ref before it
can be accepted or cleaned up during form verification.
It does not yet bind a user ID or a particular dynamic route parameter. A valid
ref can be submitted more than once; handlers own application idempotency.
Rotating `GORIBU_SECRET` also invalidates outstanding refs.

Worker uploads require matching content length and type and use an atomic
conditional put. Production streams the request body; development buffers it
for the local R2 binding, including fields with `direct: true`. Public objects
receive `Cache-Control: public, max-age=31536000, immutable`.

Production direct targets sign content type, content length and
`If-None-Match: *` and `x-amz-meta-goribu-upload` carrying the upload ID, plus
cache control for public files. They require both R2
Worker secrets and the generated account variable. Deploy checks credential
names and configures upload CORS as described above. Signed-header enforcement,
overwrite protection and browser CORS passed live checks in both default and EU
jurisdictions. Dev uses the local Worker transport.

For JSON, URL-encoded and multipart submissions, `await req.body()` replaces
each declared upload field with `{ key, name, type, size, url? }` after verifying
its ref and the stored object's metadata. `url` is present only for the public
default bucket. TypeScript apps can import `R2Upload` from `goribu/server`.
Verification is cached for the request, including calls from middleware.

Invalid or expired refs, refs for another route/field/bucket, missing objects,
arrays and plain file inputs in declared fields leave the field absent. A
missing or different stored upload ID also leaves the field absent and preserves
the object, even if its size and type match. Only an object with this upload's
ID can be removed after a size or content-type mismatch. Skipping the PUT or
receiving 409 cannot claim or delete a previous file. Storage errors fail the
request. Other file inputs keep the ordinary multipart `File` behavior.

MIME types are declared by the browser, not inferred from file contents. Keep
public media on a separate domain and add a response header rule there for
`X-Content-Type-Options: nosniff`. Store files needing moderation privately first.
Abandoned uploads are not cleaned up automatically; applications can configure
an R2 lifecycle rule for their upload prefix.
